# Niamind API

The backend API for Niamind.

The API is built with **FastAPI**, **SQLAlchemy**, **PostgreSQL**, **Alembic**, and **Redis**. It provides the application services and data layer used by the Niamind frontend applications.

The backend lives in the `backend/` directory of the Niamind repository.

## Tech Stack

* **Python 3.12**
* **FastAPI** — API framework
* **SQLAlchemy** — database ORM
* **PostgreSQL** — relational database
* **Alembic** — database migrations
* **Pydantic** — request and response validation
* **Redis** — caching and supporting services
* **Pytest** — automated testing
* **Docker / Docker Compose** — development and test infrastructure

---

# Requirements

For local backend development, install:

* Python 3.12
* Docker
* Docker Compose

PostgreSQL and Redis do not need to be installed directly on the host if they are provided through Docker.

# Installation

## 1. Navigate to the backend

From the root of the Niamind repository:

```bash
cd backend
```

## 2. Create a virtual environment

### Windows

```powershell
python -m venv .venv
.venv\Scripts\activate
```

### macOS / Linux

```bash
python3 -m venv .venv
source .venv/bin/activate
```

## 3. Install dependencies

Install the application dependencies:

```bash
pip install -r requirements.txt
```

Install development and testing dependencies:

```bash
pip install -r requirements-dev.txt
```

# Configuration

Create a local `.env` file from `.env.example`:

```text
.env.example → .env
```

Configure the database, Redis, and other application settings in `.env`.

The `.env` file contains environment-specific configuration and must not be committed to Git.

## Local Development

When running FastAPI or Alembic directly from the host machine, services should use host-accessible addresses.

For example:

```env
DB_URL=postgresql+asyncpg://postgres:postgres@localhost:5432/niamind
```

Redis should similarly point to the local Redis service:

```env
REDIS_HOST=localhost
REDIS_PORT=6379
```

The exact settings are defined by the application's configuration in `constants.py`.

# Database Migrations

Niamind uses **SQLAlchemy** for database models and **Alembic** for database migrations.

Migration files are generated during development and committed to version control.

Production and deployed environments only apply migrations that already exist in the repository.

The workflow is:

```text
Change SQLAlchemy models
        ↓
Generate migration locally
        ↓
Review migration
        ↓
Test migration
        ↓
Commit migration
        ↓
Deploy
        ↓
alembic upgrade head
```

## Create a Migration

After changing a SQLAlchemy model:

```bash
alembic revision --autogenerate -m "describe the change"
```

For example:

```bash
alembic revision --autogenerate -m "add questionnaire tables"
```

Migration files are created in:

```text
migrations/versions/
```

Always review an autogenerated migration before applying or committing it.

**Migrations should be generated locally, not in production or in the production Docker container.**

## Apply Migrations

Apply all pending migrations:

```bash
alembic upgrade head
```

Check the current migration:

```bash
alembic current
```

View migration history:

```bash
alembic history
```

Migration files are part of the application source code and must be committed to Git.

# Docker

Docker is used to run the application and its supporting infrastructure.

Start the application stack:

```bash
docker compose up --build
```

Run in the background:

```bash
docker compose up -d --build
```

Stop the stack:

```bash
docker compose down
```

When the application container starts, it applies existing database migrations before starting FastAPI:

```text
Container starts
      ↓
alembic upgrade head
      ↓
uvicorn
```

Docker **does not generate migrations**.

If a new migration has been committed to the repository, the next deployment will apply it automatically through:

```bash
alembic upgrade head
```

# Testing

The backend uses **pytest** for automated testing.

Tests are organized into:

```text
tests/
├── unit/
├── integration/
└── e2e/
```

## Unit Tests

Unit tests verify individual pieces of application logic without requiring the full application infrastructure.

Examples include:

* validation
* data normalization
* questionnaire rules
* business logic
* utility functions

Run unit tests:

```bash
pytest tests/unit
```

## Integration Tests

Integration tests verify interactions between application components and real supporting services.

These tests may use:

* PostgreSQL
* Redis
* SQLAlchemy
* application services

The test infrastructure uses separate ports from normal development:

```text
PostgreSQL → localhost:5433
Redis      → localhost:6380
```

Run integration tests:

```bash
pytest tests/integration
```

## E2E Tests

End-to-end tests exercise complete API flows through HTTP.

A typical flow is:

```text
HTTP request
     ↓
FastAPI route
     ↓
Service
     ↓
SQLAlchemy
     ↓
Test PostgreSQL
     ↓
HTTP response
```

Examples include:

* joining the waitlist
* starting a questionnaire
* submitting questionnaire answers
* completing a questionnaire
* invalid API requests

Run E2E tests:

```bash
pytest tests/e2e
```

## Run All Tests

Run the complete test suite:

```bash
pytest
```

For verbose output:

```bash
pytest -v
```

The test suite uses the dedicated `docker-compose.test.yml` configuration and `pytest-docker` to provide the required PostgreSQL and Redis services.

You normally do **not** need to start the test containers manually before running pytest.

# Current Domain

The current backend is focused on the initial Niamind platform functionality.

The core domain currently includes:

```text
Questionnaire
    └── Question

QuestionnaireSession
    └── Answer

WaitlistEntry
```

### Questionnaire

Defines a questionnaire and its questions.

### Question

Defines an individual question, including its type, options, ordering, and validation requirements.

### QuestionnaireSession

Represents a respondent's questionnaire session and connects their answers to the questionnaire being completed.

A session can identify the respondent by email while the platform is being developed.

### Answer

Stores an answer associated with both a questionnaire session and a question.

### WaitlistEntry

Stores information submitted by someone joining the Niamind waitlist.

User/account functionality is not currently part of this backend domain.

# API Architecture

The API follows a layered approach:

```text
HTTP Request
     ↓
Route
     ↓
Schema validation
     ↓
Service / business logic
     ↓
SQLAlchemy
     ↓
PostgreSQL
```

Routes should primarily handle HTTP concerns.

Business rules should live in service modules rather than being embedded directly in route handlers.

Database models should remain separate from API request and response schemas.

# Development Principles

The backend follows several core principles:

* Use SQLAlchemy for database models.
* Use Alembic for database migrations.
* Generate migrations during development.
* Review autogenerated migrations before committing them.
* Never generate migrations directly in production.
* Keep migration files in version control.
* Keep business logic out of API routes where possible.
* Keep database models separate from API schemas.
* Keep test infrastructure separate from development and production infrastructure.
* Use unit tests for isolated business logic.
* Use integration tests for application/database interactions.
* Use E2E tests for important complete API flows.
* Test database changes before deploying them.
